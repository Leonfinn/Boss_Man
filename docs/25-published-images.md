# Published images and releases

How Boss Man's ready-made images are built, published, signed and released (BOS-973; plan: BOS-935, DR-050). Nothing here names a registry or an account: the places to publish to are settings.

## What happens

- **Every merge to `main` that passes CI** runs the *Publish images* workflow (`.github/workflows/publish.yml`). It builds the images natively on x86 and ARM, pushes them once to the first registry in your list, and copies the finished image to the others **by digest**. If any copy has a different digest the run fails, so one signed `release.json` covers every registry. The images get the tag `sha-<first 12 characters of the commit>` and nothing else.
- **Each image is signed** without a key (Sigstore keyless signing, tied to the workflow run) and carries an **SBOM** and **provenance**, both attached for each architecture. Signatures and attachments are stored per registry, so the workflow checks all of them in **every** registry. It also checks that `/NOTICE` is inside each image.
- **The owner's beta button** is the *Release* workflow (`.github/workflows/release.yml`): GitHub → Actions → Release → Run workflow → branch `main` → type a version such as `0.1.0-beta.1`. Leave the optional **commit** box blank to release main's newest commit, or type the full 40-character sha of an older green main commit whose images are already published: while merges are busy main moves every few minutes and the newest commit's images are rarely finished when you press the button. A commit that is not on `main`, is not 40 hex characters or has no `sha-` images is refused before anything is tagged; the signature still comes from the workflow on `main`. It rebuilds nothing. It checks the released commit's images in every registry, gives them the version tag and the moving `beta` tag, and publishes a signed `release.json` as a GitHub pre-release. A version can be released once. If a run fails after the images were tagged but before the GitHub release was made (a half-finished run), press Release again with the same version and the same commit: the check accepts version tags that sit on that commit's own images (and nothing else), tags again (a no-op) and finishes the release. A version tag on any other image is refused: pick a new version (BOS-2601). With the commit box blank, the re-press finds the commit by itself: when the version's images already exist, Release reads the commit they were built from (their `org.opencontainers.image.revision` label) and finishes that release, not main's newest commit, saying so in a notice (BOS-2602). A commit whose `.github/workflows/` files differ from main's is refused before anything is tagged: GitHub will not let the workflow's own token create a release there (HTTP 403 "Resource not accessible by integration", see GitHub's REST docs for "Create a release"), which is what left 0.1.0-beta.2 half-made on an older commit. So a typed commit must be one whose workflow files still match main's; after a workflow change merges, release main's newest commit, under a new version if the old one is already on an older commit's images. Every refusal before tagging is also an annotation on the run page, readable without the job log.
- **The weekly beta** (BOS-2662): the same *Release* workflow also starts by itself, with nobody pressing anything. It is a `schedule:` block at the top of `.github/workflows/release.yml`, default **Tuesday 10:00 UTC** (`cron: "0 10 * * 2"`, one marked line; change it there, or delete the block to switch the weekly release off). GitHub runs it on the default branch only. A scheduled run (`scripts/release-pick.sh`, tested by `scripts/release-pick.test.sh`) looks at the newest 30 commits of `main`, newest first, and takes the first one where **CI passed** and **every image in `PUBLISH_IMAGES` is published for amd64 and arm64 and signed** (with SBOM and provenance, in every registry). A red or half-published commit is never chosen. The version is the next beta number after the newest `vX.Y.Z-beta.N` release (compared as numbers). The pre-release notes are the `CHANGELOG.md` lines added since the previous beta's commit (`scripts/release-notes.sh`): the same lines the website's "What's new" page shows, so nothing is written or pasted on release day. If no commit qualifies, or nothing new has landed since the last beta, the run ends **green** with one notice line saying why ("Weekly release skipped: ...", visible on the run's page) and makes no tag or release. A scheduled run never retries; when it fails, Boss Man's main-CI watcher (it reads every workflow's failed scheduled runs) opens a ticket for the CEO. It uses the repository from GitHub's context, so a fork gets the same behaviour once its own images are published. A scheduled run also skips (green, with the reason) when the chosen commit's workflow files differ from main's, because GitHub would refuse the release there. Before any tag, the docs gate (BOS-2666) and the image label gate (BOS-2841) can refuse it too: the label gate stops a run whose new "What's new" entries do not say "In image <version>" at the commit being released, so the page never says "not in an image yet" about an image that has them. The Release Manager labels the week's entries in the Monday docs check (scripts/changelog-label.sh label, CHANGELOG.md step 8), before the run picks its commit: a label that lands after the picked commit is not in that release, because the run releases an existing commit's images and rebuilds nothing. If a run is refused for a missing label, find out which commit it picked, label the named lines on top of it, wait for the new commit's images, and run the release again. A pressed run works as described above, unchanged.
- **`release.json`** lists each image's digest, and its digest per architecture, plus the registries, the commit, the **Claude pack hash** (`packHash`: the first 24 hex characters of the sha256 of `apps/runner/claude-pack/package-lock.json` at that commit, the same rule the runner's installer names its folder by) and the **install layout** number (`installLayout`, bumped with the updater's colour spec). The last two are new and additive: a `release.json` from before them still parses, it just has neither. The updater (BOS-941, `apps/updater`) trusts only this file: it checks the signature itself, with the `sigstore` Node package, against identity `https://github.com/Leonfinn/Boss_Man/.github/workflows/release.yml@refs/heads/main` (the repository is `BOSSMAN_UPDATER_REPO` in the release's `images.env`) and issuer `https://token.actions.githubusercontent.com`. You can check the same by hand with `cosign verify-blob`. No install starts the updater yet (941b adds the swap and the compose service), so nothing changes on a running install.
- **The updater image** (`boss-man-updater`, `apps/updater/Dockerfile`) is built and tested by CI like the others and published once it is in `PUBLISH_IMAGES`. The updater needs no registry login of its own beyond the install's pull access.

The rules are in `scripts/publish-images.sh`, tested by `scripts/publish-images.test.sh` (a fake registry, no network).

## Settings

Variables: repository Settings → Secrets and variables → Actions → Variables. Secrets: the `publish` environment (Settings → Environments → publish).

| Name | Kind | Meaning |
|---|---|---|
| `IMAGE_PREFIXES` | variable | Space- or comma-separated `<registry>/<namespace>` list; the first is pushed to, the others get a copy. Empty means `ghcr.io/<repository owner>`. Only `ghcr.io` and `docker.io` have a login step. |
| `DOCKERHUB_PUBLISH` | variable | `true` turns Docker Hub on. Once on, a `docker.io/<namespace>` entry must be in the list and both secrets must exist, or the run **fails** (it never skips). Off: `docker.io` entries are ignored. |
| `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` | secrets of the **`publish` environment** | Docker Hub account name and a read-and-write access token. Keep them in the `publish` environment (limited to `main`), never as ordinary repository secrets: agent branches run Actions too and could read a repository secret. |
| `PUBLISH_IMAGES` | variable | Image names to publish. Default: `boss-man-server boss-man-launcher boss-man-netguard`. A release that an installed updater can move to lists all five: add `boss-man-runner` and `boss-man-updater`. |

The updater image (`boss-man-updater`) is also not in the default set: add it to `PUBLISH_IMAGES` before the first release the updater is meant to read. Until it is listed, a `release.json` has no updater image and the updater refuses to move to it, which is safe (the install stays where it is).

An image added to `PUBLISH_IMAGES` is built only from the next publish on. Commits published before the edit have no image for it, and Release refuses them (naming the missing images). Re-run "Publish images" for the commit you want to release (Actions > Publish images > the run > Re-run all jobs) before pressing Release (BOS-2590).

Where to look for a signature and SBOM in the registry (BOS-2590): cosign stores the signature as a tag `sha256-<hex of the image index digest>.sig`, not `sha-<commit>.sig`, and buildx `--sbom=true` stores the SBOM and provenance as `attestation-manifest` entries inside the image index, not as a `.sbom` tag. `scripts/publish-images.sh verify` checks both and the publish job runs it, so a green publish job means both are there.

The runner image (`boss-man-runner`) is **not** in the default set. Since the Claude pack (BOS-972) it holds no Claude Code (Claude is installed on first start), so to publish it, add `boss-man-runner` to `PUBLISH_IMAGES`. The publish job then refuses the runner unless `scripts/image-tests.sh no-anthropic` passes on it (with the expected-fail marker off).

## Setting it up (any host; the account steps are on the registries' own sites)

1. GitHub's registry needs nothing in the repository: the workflow uses the run's own token. After the first publish, each package starts private. The images contain the app's source, so make a package public **only once Repo cleanup 5 is done**. Then: GitHub → your profile or organisation → Packages → the package → Package settings → Danger zone → Change visibility → Public. Do it for each published image.
2. For Docker Hub: create the account or organisation, then one repository for each published image, named exactly like the image (`boss-man-server`, `boss-man-launcher`, `boss-man-netguard`, later `boss-man-runner`). Create each as **Private** (Docker Hub defaults to public): the images contain the app's source, so switch them to public only once Repo cleanup 5 is done. Cost: Docker Hub's free plan allows one private repository, so four private repositories need a paid plan. Without one, leave `DOCKERHUB_PUBLISH` off (ghcr only) until Repo cleanup 5 is done.
3. Create an access token on Docker Hub (Account settings → Personal access tokens) with *Read & Write* permission (scope it to the published repositories if Docker Hub offers that).
4. In GitHub: repository Settings → Environments → New environment, named `publish`. Under Deployment branches and tags choose *Selected branches and tags*, add `main`. Under Environment secrets add `DOCKERHUB_TOKEN` (the token) and `DOCKERHUB_USERNAME` (your Docker Hub name). Do not add them under Secrets and variables → Actions.
5. Set the variables: `IMAGE_PREFIXES` to `ghcr.io/<your GitHub owner> docker.io/<your Docker Hub namespace>` and `DOCKERHUB_PUBLISH` to `true`.

## Checking by hand

```
docker buildx imagetools inspect <registry>/<namespace>/boss-man-server:sha-<12 characters>
```

Both registries must print the same `Digest:`. To verify a signature yourself:

```
cosign verify --certificate-oidc-issuer https://token.actions.githubusercontent.com --certificate-identity-regexp '^https://github.com/Leonfinn/Boss_Man/\.github/workflows/(publish|release)\.yml@refs/heads/main$' <registry>/<namespace>/boss-man-server@sha256:<digest>
```

## If something goes wrong

- **Undo a bad publish:** the `sha-` tags are harmless; nothing pulls them until a release. To stop publishing, set the `IMAGE_PREFIXES` variable to an unusable value or disable the *Publish images* workflow in the Actions tab. Reverting the commit that added the workflows has the same effect.
- **A release you regret:** delete the GitHub release and its tag, then re-point `beta` by releasing a newer version.
- **Docker Hub's download limit:** anonymous pulls from Docker Hub are rate-limited; GitHub's registry is not. Anyone pulling by hand can use the `ghcr.io` copy instead (the digest is identical).

# 08 — v1.2 plan: setup without the faff

The plan comes from the owner's first install and first test run on TrueNAS (17 Oct 2026). It covers 11 points of feedback, then what the first run showed (R65–R68), and the answers to the follow-up questions. Everything ships as one release, v1.2, built as a stack of reviewable PRs. Sizes are relative guesses (S/M/L).

## What the owner decided

| Question | Decision |
|---|---|
| How a company's runner is set up | **Fully automatic**, through a small dedicated **launcher** container. It is the only container that holds `docker.sock`. The server and runners never see it. |
| What replaces "Check before merging" | **Auto-detect plus presets**, with "Custom command" under Advanced. |
| How agents are hired | **Role templates**, whose instructions the CEO or the owner can tailor. |
| What needs the owner's approval | **Customisable.** By default only hires need approval. A setting can make instruction edits need it too, or neither. |
| What happens after sign-up | **A wizard**, with an "I know what I'm doing" way out. |
| How approved work lands | **A pull request** on GitHub or Gitea, merged once its checks and approvals pass. |
| How v1.2 ships | **All in one release.** |

## Why a launcher and not a socket proxy

The owner asked how Paperclip handles this, and how to avoid the risk of something taking over the NAS.
- **Paperclip doesn't start containers per company.** Its README says a local install is "a single Node.js process", and companies are kept apart by "company-scoped access checks … within one deployment" ([paperclipai/paperclip](https://github.com/paperclipai/paperclip), MIT). Agents run on the host, or on hosted sandboxes (e2b, Daytona, Modal and others). There is no container pattern to borrow. Boss Man already isolates companies more strongly, with a runner per company.
- **General-purpose Docker socket proxies don't close the hole.**
  - [wollomatic/socket-proxy](https://github.com/wollomatic/socket-proxy) (1.13.1) can limit bind-mount sources. Its docs say it does not restrict privileged containers, added capabilities or devices, and that it is "a request filter, not a sandbox".
  - Tecnativa's proxy filters by method and path. An issue on another project reports that it never inspects the request body, so a create request can bind-mount the host's root ([guise#11](https://github.com/messelink/guise/issues/11)). That's a user report, not checked against Tecnativa's code.
  - [buildkite/sockguard](https://github.com/buildkite/sockguard) refuses privileged containers and host binds by default, but it's a general policy engine to configure and keep up to date.
- **A purpose-built launcher has a smaller surface.** It accepts no Docker API at all, only "start, stop or recreate the runner for company *slug*". It builds the whole container spec itself. A compromised Boss Man server could at worst start more runners that are just as locked down, inside the company's own data folder.

## Requirements

### R55 Runner launcher (points 4, 5) — L
**The `launcher` service** (`apps/launcher`):
- It's a small Node process with no dependencies outside the Node standard library, so it is easy to audit.
- It has a read-only root filesystem, `cap_drop: [ALL]` and `no-new-privileges`, and runs as uid 1000.
- It joins Docker's socket group through `group_add`. The installer reads the group with `stat -c %g /var/run/docker.sock`.
- It publishes no ports. It listens only on an `internal: true` network shared with the server.
- The server authenticates with a key from `secrets/launcher.key`, created at install.

**Its API has exactly four calls:**
- `PUT /runners/:slug` with `{ token }`: create or recreate the runner, then start it.
- `POST /runners/:slug/restart`
- `DELETE /runners/:slug`: stop and remove the container. The data stays.
- `GET /runners`: status.

**Rules the launcher enforces itself.** None of these can be passed in from outside:
- **Slug.** `slug` must match `^[a-z0-9][a-z0-9-]{0,39}$`.
- **Image.** The image is always `boss-man-runner:current`. The launcher never pulls.
- **Mounts.** It mounts only `${BOSSMAN_DATA}/companies/<slug>/{workspaces,runner-data,claude}`, which it creates as uid 1000, plus `runner.token` read-only at `/run/secrets/runner_token`. The token file is mode 0600 and written by the launcher.
- **Security settings.** The settings are fixed:
  - user 1000;
  - `CapDrop: ALL`, `no-new-privileges`;
  - `Privileged: false`, no devices, no host namespaces;
  - `PidsLimit: 1024` and the configured memory limit;
  - `RestartPolicy: unless-stopped`.
- **Network.** It uses Boss Man's compose network only, so the runner can reach `server:3100`. Never `host`.
- **Ownership.** It only touches containers it labelled `boss-man.launcher=1` and `boss-man.company=<slug>`, and it refuses anything else.
- **Audit log.** It logs every call. It never logs tokens.

**On the server:**
- **Creating a company** issues a runner token and calls `PUT`. Settings › Runner then shows "Starting…" and then "Connected", with no copy and paste.
- **Rotating a token** writes the new one through the launcher and restarts the runner. That's a "Reconnect runner" button.
- **Updating the image.** `scripts/update-runner.sh` asks the launcher to recreate every runner after the canary passes. Rollback recreates them on `:previous`.

**Without a launcher.** The launcher is opt-in in `.env` with `BOSSMAN_LAUNCHER=1`. Without it, Settings › Runner shows a single command to paste, which fetches the token by itself. The install guide uses the launcher.

**Migration.** The existing compose `runner-app-co` keeps working. The guide shows how to hand Boss Man Co to the launcher: stop the compose runner, remove `COMPOSE_PROFILES=runners`, then click **Use the launcher** in Settings › Runner.

**Tests:**
- the launcher refuses bad slugs, unknown containers, a missing key, and any extra field in a request;
- the spec it builds is snapshot-tested to have exactly the fixed settings;
- a CI job runs the launcher against real Docker and checks the runner connects.

### R56 Setup wizard (point 1) — M
**The steps,** shown after the owner account is created:
1. Name the company and what it's for.
2. Add a project: a name and a repo (GitHub or Gitea, R59). The merge check is auto-detected (R57).
3. The runner starts by itself through R55, with a live "Connected" tick.
4. Add a Claude setup-token or API key, checked live (R58).
5. Add a git token, checked against the repo (R58).
6. Choose the funding source for the CEO.
7. Write a first ticket, optional, with the new ticket card (R63).

**Leaving and resuming.** Every step has **Skip**. The first screen has **"I know what I'm doing, let me get on with it"**, which goes straight to the board. Anything unfinished shows as a small "Finish setting up" checklist on Decisions until it's done or dismissed. Progress is saved, so the wizard resumes where it was left.

### R57 Merge check presets (point 2) — M
Settings › Projects replaces the free-text box with **"Before merging, Boss Man will…"** and a dropdown:
- **Run the tests (detected).** The runner inspects the repo:
  - `package.json` with its package manager from the lockfile;
  - `pyproject.toml` or `requirements*.txt`;
  - `go.mod`, `Cargo.toml`;
  - a `Makefile` `test` target.

  It then proposes a command, shown in plain words ("Install with pnpm, then run typecheck and test").
- **Node (npm / pnpm / yarn), Python (pytest), Go, Rust, Make.**
- **Nothing:** merge after review only.
- **Custom command**, under Advanced: today's text box.

Detection runs on the runner, which already holds the clone, when the repo is set and again on **Re-detect**. The deep check for high-risk tickets gets the same treatment.

### R58 Check buttons for keys and tokens (point 6) — S
- **Check, without saving.** The credential form gets a **Check** button that uses the existing `providerLiveValidator`:
  - for an Anthropic key, `GET /v1/models?limit=1` ([docs](https://platform.claude.com/docs/en/api/models/list));
  - for an OpenAI key, `GET /v1/models`.

  Saved credentials get a **Check again** button.
- **Git tokens** are checked against the host's API with read-only calls: GitHub `GET /user` plus the repo, and Gitea `GET /api/v1/user` plus the repo. Each reports whether the token can push and open pull requests.
- **A Claude setup-token** can only be proved by Claude Code. Its check asks the runner to run one minimal non-interactive prompt. The button says it uses a tiny amount of the subscription allowance.

### R59 Gitea, and pull requests (point 7) — M
- **Plain http.** Project repo addresses may use `http://` when the host is a private-range IP or a `.local`/`.lan` name, for a LAN Gitea such as `http://192.168.68.67:3003`. Anything else still needs https or ssh.
- **The host.** The git host type (GitHub or Gitea) is detected from the address, or from the API on a custom domain. The API base is stored with the project.
- **Pull requests.** Approved work is pushed to the ticket branch and a pull request is opened:
  - Gitea: `POST /api/v1/repos/{owner}/{repo}/pulls`;
  - GitHub: `POST /repos/{owner}/{repo}/pulls`.

  Once the merge check and approvals pass, Boss Man merges it:
  - Gitea: `POST …/pulls/{index}/merge` with `Do: "merge"`;
  - GitHub: `PUT …/pulls/{n}/merge`.

  The pull request link shows on the ticket.
- **Confirm before building.** Confirm the exact Gitea fields against the instance's `/api/swagger` before building. I only found third-party copies of the spec.
- **Protected branches now work.** The R46 note about protected default branches no longer applies.
- **Git usernames.** A per-credential `GIT_USERNAME` defaults to `x-access-token` for GitHub and to the token owner for Gitea. `apps/runner/src/workspace.ts` already sends `GIT_USERNAME:GIT_TOKEN` as HTTP Basic, so cloning and pushing need no change.

### R60 Model picker (point 8) — M
- **Where the list comes from.** The runner reports the models each agent kind offers, from the ACP session's `configOptions` (category `model`). That's how spike S2 listed them, and it covers subscription logins. For API-key funding, the server also lists `GET /v1/models`.
- **Freshness.** Lists are cached per company and refreshed on runner connect and by a **Refresh** button.
- **The picker.** The model field becomes a dropdown: Default, then the reported models by display name with the ID underneath, then **Other…** for a typed ID. An ID that's no longer offered shows as "not offered by this runner".

### R61 Risk explained (point 9) — S
- **A help popover** next to Risk, on the new ticket card and the ticket page. It gives one line per tier: who reviews, which check runs, and whether it deploys to staging first. It is built from the same R48 rules the server uses, so it can't drift.
- **The board badge** gets a tooltip with the same line.

### R62 Agents tab and hiring (point 10) — L
**The Agents page** lists each agent: role, model, funding, status, current ticket, and cost this month. It has **Hire**, **Edit** and **Retire**.

**Role templates** cover CEO, Engineer, Researcher, Designer, QA and Writer. Each has:
- instructions;
- a suggested model tier;
- suggested tools and permissions;
- a default risk ceiling.

Templates are a starting point. The owner or the CEO can tailor any agent's instructions.

**The CEO can hire through its MCP tool.** It calls `agents.propose_hire` with a template, a name, instructions, a model and funding, and `agents.update_instructions` to change an agent. What needs the owner's approval follows a setting in Settings › Agents:
- **Hires only.** This is the default. A hire waits in Decisions, and an instruction edit goes through with a notification, a diff and an **Undo**.
- **Hires and instruction edits.**
- **Nothing.** Everything is recorded in the agent's history.

Approved hires take the company's funding and budget rules as they are.

**History.** Every change, by the owner or by the CEO, is stored with its diff.

### R63 New ticket card (point 11) — S
On the board, **New ticket** is just a button. It opens a card with:

Ctrl/Cmd+Enter saves. Unassigned is the default, so nothing starts by accident. The ticket page's description editing and assignee picker (#44) are kept.

### R64 Copy buttons on plain http (point 3) — S
- **Why copying fails.** `navigator.clipboard` exists only in secure contexts (HTTPS or localhost). On `http://<nas-ip>` it's undefined, so the copy silently did nothing ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard)).
- **The fix.** One `copyText()` helper used by every Copy button:
  1. Use the Clipboard API when `window.isSecureContext` is true.
  2. Otherwise select the text in a read-only field and use `document.execCommand("copy")`. It is deprecated but still supported.
  3. If that fails too, leave the text selected and say "Press Ctrl/Cmd+C".

  It always says whether the copy worked.
- **Fewer tokens to copy.** R55 removes the runner token copy.

### R65 Chat with agents on a ticket (owner, 17 Oct) — M. *Built in #49.*
- **The thread.** Each ticket page gets a **Conversation** with its agents, like Paperclip's ticket comments. Messages are stored in a new `ticket_messages` table: ticket, author (owner or agent), text and time.
- **Owner messages.** A message from the owner goes to the ticket's assignee:
  - into the run that's working on the ticket, using steering (R37);
  - or, if no run is going, a wake on the ticket with the message as its note.
- **Agent replies.** Agents reply with a new MCP tool, `ticket_reply`, and their reply shows in the thread. The final message of a run on the ticket is also added as a reply.
- **Untrusted text.** Text from outside, through the portal or engagements, stays wrapped as untrusted (R51).

### R66 Fixes from the first test run (17 Oct) — S. *Built in #47.*
- **Own answers.** An agent's question can be answered in the owner's own words. Decisions that act on their answer keep their options.
- **Tickets move.** A run starting on a backlog or ready ticket moves it to In progress.
- **Runs say why.** The Runs page says why each run started.

### R67 Tokens for subscription runs (owner, 17 Oct) — M
- **What the page shows.** Money means little on a subscription. Runs paid from a subscription show **input and output tokens** (plus cache reads and writes on hover). Runs on API credit keep showing cost.
- **Where the counts come from.** The runner adds up `PromptResponse.usage` from each turn of a run (inputTokens, outputTokens, cachedReadTokens, cachedWriteTokens) and reports the totals when the run ends.
  - claude-agent-acp 0.91 fills this in.
  - The protocol marks the field unstable, so a run without it shows "not reported".
- **Storage.** The totals are stored on the run.
- **Funding page.** It shows tokens this window for subscriptions, next to the existing 5-hour and 7-day quota bars.

### R68 Runaway CEO runs (17 Oct) — S, cause to confirm
In the first test, the CEO started a new run with no ticket about every minute, from 18:17 to 18:21, at about $5 each. The cause isn't known yet; the owner's `wakes` table will show it. Whatever the cause, the fix should add a guard: no more than N runs with no ticket per agent per hour, with the owner told when it trips.

**Note:** the CEO's own tickets from that run are numbered R55–R60. Those numbers clash with this plan's. Agents should get the next free number from Boss Man, or not number requirements at all.

### R69 Wiki and what tickets produce (owner, 17 Oct) — M. *Built in #50.*
"See the evidence" on the research note only opened the ticket; the document itself was on an unmerged branch.
- **Wiki.** Each company has Markdown pages in nested folders ("Research/Competitors"), written by the owner or by agents with a new `wiki` tool. Every save keeps a revision that can be put back. Pages render with react-markdown, which ignores raw HTML.
- **What a ticket produced.** A page written with a ticket's id shows on the ticket under "What it produced". Agents can also attach a repo file (path and branch or commit) or a web link.
- **Evidence links.** `notify_owner` takes a link to an in-app page, so a note opens the work itself.
- Paperclip's closest feature is per-issue documents with an Artifacts page; its docs site couldn't be reached to check for a wiki, so the folder design follows the owner's description.

### R70 Chat as a team messenger (owner, 17 Oct) — M. *Built in #51.*
- **Layout.** Like WhatsApp or Slack: team members on the left, the conversation on the right. The CEO is first, as most messages go there; any agent can be messaged directly.
- Each agent's direct chat runs like today's owner chat: its own folder, board tools only, outside the CEO's chapters, one run at a time per agent.

### R71 Skills (owner, 17 Oct) — L. *Built in #54.*
- **The library.** Each company has a library of Agent Skills folders: a SKILL.md with name and description frontmatter, plus any files it needs ([Claude Code skills](https://code.claude.com/docs/en/skills)). The Skills page is in the Company group.
- **Ways in.** Skills come from a **GitHub link** (a repository, folder or SKILL.md; every skill under it is added, pinned to the commit; "Check for updates" re-reads it), are **written** in Boss Man, or are **uploaded** as a folder, files or a .zip. Only public repositories are supported for now.
- **Who has it.** The owner ticks who has each skill. The CEO can give and take skills with a new `skills` tool, and the owner is told each time. The approval setting from R62 applies once that's built.
- **At run time.** A Claude agent's run carries its skills. The runner writes them to a folder of their own (`<dir>/.claude/skills/<name>/`) and passes it to the session as an extra directory, so the repo worktree and the shared home stay clean; the folder is removed when the run ends. A runner test with the real Claude Code and a stub model confirms the skill's description reaches the model.
- **Limits.** Codex agents don't get skills yet, and nor do chat runs, which have no built-in tools.
- Paperclip's company skill library works the same way (import from GitHub pinned to a commit, or from other sources; attach to agents) ([Paperclip skills](https://docs.paperclip.ing/guides/org/skills)).

### R72 Company switcher (owner, 17 Oct) — S. *Built in #53.*
A switcher at the top for moving between companies, like Paperclip's. The chosen company applies to every page, replacing each page's own company dropdown.

### R73 Wiki maintainer (owner, 17 Oct) — S. *Built in #52.*
- Every company gets a **Wiki Maintainer** agent, created **paused**, with no model. The owner chooses its model and presses Start (Settings → Agents); starting it without a model is refused.
- When a ticket finishes, the maintainer is woken (one waiting run covers every ticket finished before it starts). Its prompt lists the tickets finished since its last run and what each produced. Its job is to keep an Index page, file pages into folders, merge duplicates, link documents to their tickets, and tell the owner when something needs doing. It doesn't create tickets or change code.
- Any agent can now be paused and started; a paused agent's work waits.
- Paperclip documents per-agent pause and resume; nothing was found on a wiki-maintainer agent there, so this follows the owner's description.

### R76 Ticket page: folding sections, properties column, live activity (owner, 17 Oct) — M. *Built in #58.*
- **Two columns.** Description on the left, with a **Properties** column on the right like Paperclip's: status, assigned to, risk, project, branch, created and last activity.
- **Folding.** Everything else folds behind an arrow and starts closed: what it produced, plan, roadmap and dependencies, changes, review. Each shows a hint when closed ("1 item", "waiting for you").
- **Activity.** One feed of the conversation and each run's progress, oldest first. A running run shows its steps live; finished runs fold away. The box at the bottom sends after the agent's current step, or **Interrupt and send**, or **Stop**.

### R77 Agents can look tickets up (owner, 17 Oct) — S. *Built in #57.*
The Wiki Maintainer couldn't read the wiki from chat, or open another ticket, so it left notes instead of doing the work. Every run, chat included, now has a `tickets` tool (find, read, and read a file from a ticket's branch through the runner), and chat runs get `wiki` and `skills`. Prompts tell agents to look things up and resolve what they can.

### R78 Limit estimate and daily use (owner, 17 Oct) — S. *Built in #59.*
Ideas from [claude-dashboard](https://github.com/uppinote20/claude-dashboard) (MIT, ideas only); no code taken.
- **Limit estimate.** Under each quota bar, the Funding page says how fast the window is filling and whether it lasts until it resets ("Runs out at about 16:40 at the recent rate").
  - The rate comes from the readings in the current window over the last two hours.
  - It needs readings at least 5 minutes apart; otherwise nothing is shown.
  - It's an estimate: it assumes use carries on as it has.
- **Alert.** When a window is at least half used and set to run out before it resets, the owner gets one "flag" notification for that window.
- **Daily use.** Each funding source shows the last 7 days as bars: tokens for a subscription, money otherwise, with the run count on hover. Days are UTC.
- **Later.** A forecast line on the Dashboard's subscription tile, once #55 (subscription spend on the dashboard) is merged.

### R79 Plugins (owner, 17 Oct) — L. *Roadmap only, not for building yet.*
A plugin bundles tools that agents can use: an MCP server, a CLI, skills, or several of these. The owner adds a plugin once and gives it to agents, the same way skills work (R71).
- **First example: [open-pencil](https://github.com/open-pencil/open-pencil)** (MIT), an open design editor with AI tools.
  - `@open-pencil/mcp`: an MCP server over stdio, plus HTTP at `127.0.0.1:7600/mcp`.
  - `@open-pencil/cli`: a command line for the same tools.
  - An agent skill, added with `npx skills add open-pencil/open-pencil`.
  - Parts of it need Node 22.15 or later.
- **What a plugin needs from Boss Man** (to design when this is built):
  - a manifest: name, version, source, what it adds (MCP servers, CLIs, skills) and what it needs (Node version, network, files);
  - install on the runner, not the server, pinned to a version;
  - per-agent grants, with each MCP server added to the agent's ACP session;
  - the policy engine and risk tiers (R48) still apply to every tool a plugin adds.
- **Open questions.** Whether plugins run in the runner's container or their own; how updates are approved; how a plugin's network access is limited.

## Risks and open questions
- **The launcher holds `docker.sock`.** Anything that can get code into the launcher can control Docker. To limit that:
  - it has no inbound port;
  - its key is shared with the server only;
  - it has a read-only filesystem, no shell in the image (distroless), and no dependencies outside the Node standard library;
  - a fixed spec is checked by tests.

  The owner accepted this trade-off on 17 Oct 2026. The earlier rule "never mount docker.sock" now reads: never into the server or a runner.
- **The TrueNAS socket group.** The socket's group and path on TrueNAS 25.10 need checking on the NAS (`stat /var/run/docker.sock`). I haven't confirmed them.
- **Gitea API fields.** Check the pull request and merge fields against the owner's Gitea version through `/api/swagger` before building R59.
- **Setup-token check.** A setup-token check spends a little allowance, so the button says so and never runs on its own.
- **Model availability.** The models listed through ACP depend on the Claude Code version in the runner image. The list is per runner, not global.

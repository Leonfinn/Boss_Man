# Runner network guard (netguard, BOS-324)

**For owners, in short.** The guard stops agents reaching your home network. It is on by default and needs nothing from you. Boss Man opens the addresses it needs by itself: the server, your DNS servers, each company's tool servers and each project's git host. You see them under Settings → Server and runner → This server → **Network guard**.

- **Agents need another service on your network** (Penpot, for example): add it to `.env` as `BOSSMAN_NETGUARD_ALLOW="host:port host:port"` (one line), then run `scripts/update-runner.sh --settings` from the checkout. The Network guard section lists it once it is live.
- **Turn the guard off:** see "Roll back" below.

The rest of this page is how it works.

A runner container can no longer reach private networks. Agents run shell commands in the runner, and before this they could open the database (`db:5432`) or any machine on the home network. DR-004 (the wiki) explains why this is done per container and not per agent session: Landlock filters ports, never addresses.

## What it does
- The launcher starts a second small container, `boss-man-netguard-<company>`, **inside each runner's network namespace** (`network_mode: container:<runner>`). It has `NET_ADMIN` and nothing else; the runner keeps no capability (`CapAdd: []`).
- It installs one nftables table, `inet bossman_netguard` (covers IPv4 and IPv6), on the runner's outbound traffic:
  - allowed, in this order: loopback (this is also Docker's DNS at 127.0.0.11); TCP to the Boss Man server's addresses on the server's port (from `BOSSMAN_RUNNER_URL`); TCP to the company's **tool servers** and to any owner-listed host:port (below); port 53 to the DNS resolvers the host uses (read from the runner's `resolv.conf`, including a router or Pi-hole on the home network). Addresses are looked up again every 15 s by the guard;
  - refused with "administratively prohibited" (so it fails fast, not by timeout): 10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16, 0/8, 192.0.0/24, 198.18/15, `fc00::/7`, `fe80::/10`, IPv4-mapped `::ffff:0:0/96`, NAT64 `64:ff9b::/96`, documentation ranges.
  - everything else (the public internet) is untouched.
- There is no "established connections stay" rule: a connection opened while no guard was up (a runner restart leaves a short gap) is cut off the moment the rules load.
- The rules are reapplied atomically (add, delete, add in one `nft -f`), so running the script twice is safe.
- **Tool servers stay reachable.** The server tells the launcher each company's registered tool servers (crawl4ai, scrapling, Penpot, …) as host:port, when a runner starts and whenever one is added or removed. The launcher keeps them in `companies/<slug>/netguard/allow`, a folder only the guard mounts (read-only), never the runner. Only those host:ports open, not whole networks. For other things agents must reach on the LAN or tailnet, set `BOSSMAN_NETGUARD_ALLOW="host:port host:port"` on the launcher (compose passes it through).
- **Penpot is opened from its address (BOS-1582).** The host:port in the company's `PENPOT_URL` grant (set in Settings → Tools and deploys → Penpot, or granted by hand on the Secrets page before that form existed) joins the same per-company allow list (`launcher.allowFor`, through `secrets.grantedValue`). Only http(s) addresses, never one of Boss Man's own service names, and only that host:port. It is trusted for private addresses only when it is a LAN address (private IP literal or LAN-style name, `isLanHost`), the git-host rule, so a public name later re-pointed at a private address is dropped. The list is sent again whenever a `PENPOT_URL` grant or its secret is added, changed, revoked or deleted (`secrets.onGrantChange`), and at every runner start and server start, so no `.env` line is needed.
- **A name re-pointed at a private address is dropped (BOS-708).** An allow entry is looked up again every 15 s, so a public name that later resolves to a private, loopback, link-local or CGNAT address (a service on the stack's own `172.18.x` network, say) could otherwise open a way onto it. The guard drops such an address and logs it, unless the entry is one the owner meant for a private address: a private IP literal (which can't be re-pointed), the server's own address, any `BOSSMAN_NETGUARD_ALLOW` entry, a git host the owner set, or a tool server whose import used the "allow private addresses" tick (stored as `mcp_servers.allow_private`, written as a `private` marker in the allow file). The owner adding a tool server at a private host is trusted the same way; a public name they add is not. Tool servers registered before this deploy keep the old, looser behaviour when the `allow_private` migration (`apps/server/drizzle/*_allow_private.sql`) runs: it marks trusted only those whose address is a private IP literal or a LAN-style name (a name with no dot, or a `.local/.internal/.localhost/.lan/.home/.docker` name), the same rule the server applies without DNS; a public name added before the deploy stays untrusted, so re-pointing it can't open the stack network.
- **Git hosts stay reachable.** Each project's repo address (`projects.repoUrl`) gives a host:port (http 80, https 443, ssh 22 or the port in the address) that goes in the same allow file, so a company's runner can clone from its own LAN git server. Only that host and port open, only for that company; changing the repo address or archiving the project updates the list within 15 s, no restart. Nothing is hardcoded. Only the owner sets a repo address, and whatever host:port it names (even an internal service) opens to that company's runner, so set it only to the real git server. A git host the owner sets is trusted for a private address (stored as `projects.allow_private`), so a LAN git server keeps working; a git address that arrives in an imported company package is not trusted unless the import preview flagged it and the owner ticked "allow private addresses" (BOS-708), so re-pointing an imported name can't open the stack network. Entries the launcher would refuse (an underscore in the host, port 0, IPv6 literals) are left out so one odd address can't break the company's list. When the server starts it sends every runner its list once, so a deploy needs no reconnect.
- **Every address the guard opens is shown (BOS-770, BOS-791).** Settings → Server and runner → This server → **Network guard** has two lists. *Allowed automatically* (BOS-791) is every address Boss Man opens by itself, from the same data the guard is sent (`launcher.allowFor`), never a second copy: each company's tool servers, each project's git host and each company's Penpot (BOS-1582). Each row gives host:port, what it is (a tool server's name, a project's name as its git host, or Penpot) and the company it is for (a company's entries are only reachable from that company's runners). A name the guard drops (the BOS-708 rule: it resolves to a private address and isn't trusted for private) is shown as **not allowed** with a plain reason, so a missing tool server or git host is visible rather than silently absent. A tool server is trusted when the owner trusted it (`mcp_servers.allow_private`, the same value `allowFor` sends); a git host is trusted only on a LAN address (private IP literal or LAN-style name) with the project's flag on, exactly as `allowFor` decides, so a public git name that resolves privately is shown as not allowed too (BOS-777). A Penpot row is trusted exactly as `allowFor` sends it (LAN address only). The other add-ons (ntfy, Tailscale) are not opened by the guard on their own, so they don't appear. *Extra lines from your .env* is the `BOSSMAN_NETGUARD_ALLOW` list: the launcher reports the entries it started with (`GET /netguard`: mode and host:port list, nothing else), the host deployer reports each line in `.env` (host:port tokens only, in `host.json` as `netguardEnv`), and an entry a tool server, a project's git host or a company's Penpot already covers is marked "already allowed by Boss Man; this line can go". Both lists warn when the variable is on more than one line (Compose uses only the last, so an earlier one is silently ignored), and when the launcher's list differs from `.env` now (it reads `.env` only when recreated). Matching is on the literal host:port, so an IP entry and a host name for the same machine are not matched. Only host:port and names are shown, never a URL, a path or a token. It only reports: it never edits `.env` and raises no card.
- **No guard, no runner (by default).** The launcher waits until the guard's rules are loaded (its healthcheck) before it counts a runner as guarded. If the guard can't start for a runner it has just made (which holds no work yet), the launcher removes that runner and reports the error; a drain's swap then retries it (BOS-382).
- **Hosts that can't run it.** If this host can't load nftables rules (some Proxmox LXC containers, kernels without nf_tables), a probe table can't be created and the guard stops with exit code 3 (only then) and says so in `docker logs boss-man-netguard-<slug>`. `BOSSMAN_NETGUARD` then decides: `auto` (default) means **no guard on hosts without nftables**: it keeps the runner running unprotected and shows `guard: "unavailable"` in the launcher's runner list and a log line; `enforce` refuses to start runners; `off` never starts a guard (`guard: "off"`). Every other failure (missing image, rules not loading in time, a ruleset nft refuses, which exits 4) means no runner, on create, restart and the background reconcile alike: no guard, no runner.
- A runner that restarts by itself gets a new network namespace. The launcher watches Docker's container events, so it starts the guard again at once (well under a second) rather than waiting for its 5 s check; the 5 s check stays as the backstop for anything the event stream misses (a reconnect, a Docker restart). Between such a restart and the guard being back, new connections to private addresses are possible for that moment, and a connection opened in the gap is cut when the rules load (BOS-335). Settings → Server and runner → Runner shows a warning when a runner's guard is `off` or `unavailable`.
- **A running runner is never removed because of its guard (DR-007, BOS-382).** If the guard stops but the runner didn't restart, its rules are still in force: the launcher restarts the guard only, with backoff, and reports `retrying`. If the runner restarted (new namespace, no rules) or the owner's Restart left it without a guard, the launcher pauses it (its work and files stay, and it stays off its network), retries the guard and unpauses it once the rules are loaded. After 2 minutes without a guard it reports `frozen` with the reason. A host that can't pause containers gets the runner stopped instead, kept, and reported `frozen`. The guard image is checked before the old guard is removed. The launcher records which runner start the rules belong to in `netguard/guarded-for` beside the allow list.
- Guard work for one company is done one step at a time (start, restart, recreate, remove and the 5 s check never overlap).

## Build and update
The guard is not a service of its own: it runs beside each runner, started by the launcher as `boss-man-netguard-<company>`, outside the compose project, so a Docker dashboard lists it (and the runner) under "No Project" rather than with the Boss Man stack. We don't label them into the compose project on purpose: Compose would then treat them as orphans and `docker compose up --remove-orphans` would delete them. Settings → Server and runner → Runner shows per runner whether its guard is running. The `netguard` entry in `docker-compose.yml` is build-only (profile `build`, BOS-1156): it exists so `docker compose build netguard` makes the image, and `up` never starts it. If a host still has an old "Exited (0)" `…-netguard-1` container from before that change, remove it once with `docker rm <name>`; it is not a guard. The "update check failed" badge some dashboards show on the runner and guard containers is expected and harmless: the images are built on this host and exist in no registry, so there is nothing to compare. Update them with **Build and update runners**, not the dashboard.

`docker compose build netguard` builds `boss-man-netguard:current` (naming it is required; a bare `docker compose build` skips it); `scripts/update-runner.sh` rebuilds it on every runner update, and a change under `apps/netguard/` counts as a runner change in `deploy.sh` and the host deployer. Since BOS-335 that script also rebuilds and recreates the launcher when one is running, so Settings → Server and runner → Updates → **Build and update runners** puts a launcher change live too; it restarts only the launcher, never the runners. CI builds it and `scripts/ci-launcher.sh` proves the behaviour against real Docker: the server answers; the database (IPv4 and IPv6), the network gateway, 192.168.1.1, 169.254.169.254 and `fd00::1` are refused; and the guard returns after the runner restarts.

## Check it by hand
```sh
docker exec boss-man-runner-<slug> curl -s -m 8 -o /dev/null http://db:5432/; echo $?   # 7 means blocked
docker logs boss-man-netguard-<slug>
docker run --rm --cap-add NET_ADMIN --net container:boss-man-runner-<slug> -e NETGUARD_ALLOW=server:3100 boss-man-netguard:current --print   # prints the rules
```

## Roll back
- Stop guarding for good: set `BOSSMAN_NETGUARD=off` in `.env`, then run `scripts/update-runner.sh --settings`. It restarts the launcher so it reads `.env`, then swaps each runner when its company is idle. New runner namespaces then start with no rules.
- Removing the guard container with `docker rm -f boss-man-netguard-<slug>` does **not** lift the rules: the table lives in the runner's network namespace and stays until the runner restarts. The launcher also starts a new guard within 5 s.
- To go back to the code before this change, deploy the commit before it.

## Known limits

- If a host gives Docker networks global unicast IPv6 addresses (not ULA), services on them stay reachable over IPv6: only fc00::/7 and the other special ranges are blocked.
- Tool servers and project git addresses from an imported company package are checked at import (flagged in the preview and refused unless the owner ticks "allow private addresses"); once allowed, the tick is kept per server or project so the guard doesn't drop it later (BOS-708). An existing project's git host keeps working after the deploy: the same `allow_private` migration trusts every project that already had a repo address.
- Published host ports reached through a public address of the host are not blocked (only private ranges are).
- Not covered: a runner using `network_mode: host` (the launcher refuses it).

## No proven guard, no agent run (DR-049 point 1, BOS-938)

The launcher's `BOSSMAN_NETGUARD=auto` can start a runner without a guard on a host that can't load the rules, and a runner started by hand through Compose never gets one. The server no longer lets that carry on quietly. The scheduler is the one place that launches runs (work, CEO and chat runs), and it holds a wake until the runner's latest report proves both:

- **the fence** works (`partial` or `full`), unless the owner chose to run without it; and
- **the network guard is on**: the runner's own probe (DR-049 point 2: a connect to its gateway is refused at once) says `on`.

A runner that has not reported yet, or whose last report is older than 15 minutes, proves nothing, so its runs wait too. A held wake shows its reason on the board ("held: this runner can't keep agents off your home network, ..."). The owner's chat with the CEO and the PA have no file or shell tools and still start.

**The owner's choice.** For each missing feature, Settings → Server and runner → Runner shows one card with two buttons: **Keep agents stopped** (the default) and **Run agents without the network guard** (or **without the fence**). The same two options arrive as an owner card (once per episode; it goes by itself when the feature is proven). The choice is recorded with the runner's platform fingerprint: kernel version, Docker version and OS type. The runner reports its own kernel; the launcher tells it the daemon's Docker version and OS type (`BOSSMAN_HOST_DOCKER`, `BOSSMAN_HOST_OS`). A runner started by hand has no launcher, so it reports those two as `unknown`. A different host, kernel or Docker version no longer matches, so the owner is asked again. An Off chosen in Settings → Permissions → Agent fence has no fingerprint and stays until changed.

**Per host.** The rule is the same everywhere. Docker Desktop and any hand-run Compose runner will show the card until the owner chooses, because neither can prove the guard. The server's `main.ts` turns the gate on (`requireRunnerProof`); only tests that connect a stand-in runner with no report leave it off.

**Roll back.** Revert the BOS-938 commits. The migration only adds three empty columns to `companies`; nothing needs undoing in the data.

## When a runner is removed because its guard failed (BOS-467)

"No guard, no runner": if the guard doesn't load its rules (for example 20 s is not enough while a deploy has the host busy), the launcher removes that runner. Before BOS-467 it stayed gone until the owner started it by hand.

- **Self-heal.** A company with a `runner.token` file but no runner container is one the launcher removed and the owner did not stop (Stop deletes the token). Every 5 s the launcher makes it again, waiting 10 s, 20 s, 40 s … up to 5 min between failed tries. Look for `runner made again after it was removed` and `could not make runner again; will retry` in the launcher log.
- **Never retried:** a company whose guard exits with code 3 in `enforce` mode (this host can't load the rules; retrying cannot help), and any runner the owner stopped.
- **Telling people.** The server's runner watch (`services/runner-watch.ts`) pages the owner and raises a card in that company when a runner is offline for 3 minutes, and withdraws both when it reconnects. After a server restart it says once whether every runner came back within 5 minutes.
- **Watch details (BOS-497).** A runner registered by hand on a server that also has a launcher still pages: its company is counted as wanted when the launcher was never given it, or when its runner was seen connected while the launcher didn't run it (kept as a `runner-hand:<company>` setting; Stop through the launcher removes it). An offline runner the launcher doesn't want and that was never seen running by hand is an old stop: its last-seen time is cleared, so it stays quiet even when the launcher can't be reached later. After an update hold lifts, runners get the usual 3 minutes from the lift, and the 5-minute deploy check also counts from the lift. The owner is paged once per outage, even across a server restart (a `runner-offline-paged:<runner>` setting, removed on reconnect); the company's card is tried again every pass until it is raised. At server start the launcher's runner and token for a company that no longer exists are removed, so its self-heal stops retrying them.
- **Roll back:** revert the commits for BOS-467; the launcher goes back to remove-and-stay-down. No data or migration is involved.

### Per host

The mechanism is the same on every host: the launcher, Docker and the token files. Only whether the guard exists differs.

- **TrueNAS (Docker/Apps), plain Linux, Proxmox VM:** the guard loads (nftables in the kernel), so self-heal applies.
- **Proxmox LXC:** usually has no nftables inside the container. In `auto` mode the guard is "unavailable", the runner starts unguarded and is never removed for a guard failure, so there is nothing to heal. A runner that is offline there is a stopped container: use Settings → Server and runner → that company's runner → Start / Reconnect, or have the container set to restart on boot (`docker update --restart unless-stopped <container>`, name from `docker ps`).
- After a host or VM reboot, runners come back with Docker's restart policy and the guard is added again by the launcher within 5 s.

# Boss Man: before you hand work in

> This file is for the AI agents that build Boss Man inside Boss Man itself. It names their merge gate, check queue and roles (the CEO is the agent that runs the team; DR-003 is an internal decision record). If you are a person reading the code, start with [README.md](README.md) and [CONTRIBUTING.md](CONTRIBUTING.md).

Inside an agent session `scripts/check-all.sh` refuses to run (exit 2): the full check runs at the merge gate only for high and critical tickets (see "What the merge gate runs" below), and a hand run fills its one-slot queue. Run `scripts/check-quick.sh` from the repo root for your branch instead, and fix anything it reports before you move a ticket to review (reviewers run it too). It works out what your branch changed against `origin/main` and runs only what that touches, in 2 to 5 minutes: first the list guards (the in-memory-state lint, then the wake-class, owner-control and screen-inventory lists in `scripts/check-guards.sh`; each runs only when its files changed, and a failure names the file and the line to add), then the merge check, the migration lint, a check that no two guides in `docs/` share a number, typecheck of the touched packages, the vitest files related to your changes, ShellCheck when shell scripts changed, and the web build when web code changed. It prints one PASS or FAIL line per step. Typecheck and vitest wait for the merge gate's one-slot check lock ("waiting for a free check slot"), so a run may queue; do not start another or kill it. If your change touches app.ts, main.ts or mcp.ts, or more than 15 test files are related, it prints `SKIP related tests` (the gate runs them); `CHECK_QUICK_FORCE_RELATED=1` forces them, and the merge gate's own run (BOSSMAN_MERGE_CHECK set) never skips. Set `CHECK_ALL_FORCE=1` for a full run only if the CEO asked for one (for example a ticket the gate has bounced twice, or a change to `check-all.sh` or the test setup). Humans and the merge gate are unaffected.

Compose files and CI workflows are checked too, so do not write "no Docker here, CI is the real proof" for a structural slip. When a branch changes `docker-compose*.yml`, `deploy/*.yml` or `.github/workflows/*`, check-quick runs `scripts/check-compose.sh`: `docker compose config -q` (every profile on) over each file set a host loads (base, host overlays, deployer, blue/green, Tailscale, staging, ntfy, Penpot) and `actionlint` on the workflows, and a failure names the file and line. The runner has the Docker CLI and compose plugin only: no daemon and no socket, so nothing can start a container and `docker ps` still shows nothing; the deployer's fake-docker tests cover command output. A runner image from before this prints `SKIP compose and workflow validation` until the owner runs Build and update runners. You can run `scripts/check-compose.sh` alone for a quick look.

When the server-owned check queue is on (the owner's switch in Settings → Server and runner → Limits and checks → Checks, DR-003), `request_check` is the way to run your quick check: commit, then call the `request_check` tool (`scope: quick` by default; `full` only in the cases above). Use it for a check in the middle of the work. When your code is finished, do not request a check and wait in In progress: move the ticket to review. Boss Man queues the quick check itself and holds the ticket in Review as "Being checked" (BOS-1906); a pass opens the reviews, a failure sends it back to you with the failing step. A sweep also moves an In progress ticket with only its quick check of the branch head queued or running, and no run of its own, into Being checked (BOS-2114). The runner runs it outside your session, so it survives the end of your run and no agent can stop it, a pass on the same code is reused, and you are woken with the result. Do not poll, start your own background loop, or also run `scripts/check-quick.sh` by hand: a hand run takes runner memory beside the queue's checks. The tool tells you if the queue is off; only then run `scripts/check-quick.sh` yourself as above. The merge gate runs its own check per merge attempt: the full check for high and critical tickets, check-quick for the rest (see "What the merge gate runs" below).

In an agent session a whole-package or whole-suite vitest run (`pnpm test`, `pnpm --filter X test`, `vitest run` with no file, `vitest related` over app.ts, main.ts or mcp.ts) is refused by `scripts/vitest-guard.mjs`; `CHECK_ALL_FORCE=1` overrides.

### Running one test file (authors and reviewers)

Run the test files a change adds or touches, by path, from their package folder:

```
cd apps/server && npx vitest run test/foo.test.ts test/bar.test.ts
```

Up to 3 test files named by path run at once, with one worker, without waiting for the merge gate (the "quick lane"). They wait instead only when the runner is short of memory (under 6.5 GB free) or two other quick runs are going; then the run prints `vitest-guard: this run waits in the merge gate's check line because …`, followed by its place in line every 30 s. Anything else that names tests (more than 3 files, a bare word like `vitest run foo`, which is a filter, `vitest related`, `--changed`, `--maxWorkers`) waits in that line from the start, behind merge checks of 30 to 50 minutes each. So name the files; don't wrap the command in `timeout` (it kills the run without a word) or run it in the background. Do not use `BOSSMAN_VITEST_NO_SLOT=1`: it drops every memory limit and is only for when the CEO asks. If the tests still did not run, say so in your verdict.

The full check, `scripts/check-all.sh`, takes 30 to 50 minutes and runs everything CI's `check` job does that works without Docker: the script tests and lints, the list guards (the in-memory-state lint and `scripts/check-guards.sh`, before the typecheck), `pnpm typecheck`, `pnpm test`, `pnpm build`, ShellCheck (`scripts/check-shell.sh`, where info-level findings fail too) and the shell scripts' tests (`scripts/test-shell.sh`).

### What the merge gate runs, by risk tier

- **High and critical** tickets (`deepChecks` in `packages/shared/src/risk.ts`): the cheap steps of `scripts/check-quick.sh`, then the full check above. Since BOS-1939 the full check skips ShellCheck and the shell tests (about 6 minutes) when the branch, compared with `origin/main` (`BASE` overrides), changed no file they read: any `*.sh`, `scripts/`, `deploy/`, `apps/runner/`, `apps/netguard/`, `skills/penpot/`, a Dockerfile, `docker-compose*.yml`, `.github/workflows/`, root `package.json`, `pnpm-lock.yaml` or `pnpm-workspace.yaml` (the list is in `scripts/shell-tests-needed.sh`, with how it was found; its test fails if a shell test names a repo file the list misses). It prints `check-all: shell tests: skipped, no file they test changed` and records the steps under `skipped` in the result, not as passed. A hand run (`CHECK_ALL_FORCE=1`), a run on main, and a run whose changed files can't be listed run them as before; GitHub CI always runs them.
- **Trivial, low and medium** tickets (most merges: at most 47 of 497 passed merge checks were full checks): only `scripts/check-quick.sh` with `BOSSMAN_MERGE_CHECK` set. That never skips related tests, and since BOS-1732 it also runs every "whole-repo" test of each package the branch touches (a shared-code or root-config change touches all of them). A whole-repo test is found by what the file contains, not from a list: it reads repo files by path (a read call such as `readFileSync` plus `import.meta.url`, `__dirname` or `process.cwd()`, directly or through a helper in its `test/` folder), or, in `apps/web`, it renders the built app in a browser (it uses `real-page`, `playwright` or `chromium`). A test that reads files of another package by path (found from the package paths its text names, and its helpers' text, which may be aliased or nested) also runs when only that package changes (BOS-1789). A whole-repo test that names a changed file outside the packages by its repo path (`deploy/check-worker/compose.yaml`, `docker-compose.yml`) runs too, even when the branch touched no package (BOS-2286). A change to `packages/shared/src/` also runs, in launcher, runner, server and web, the tests that use a value name the changed file (or a shared file importing it) exports, and the tests that import such a user directly, except through a hub file more than 50 tests import (`app.ts`, `mcp.ts`, `db/schema.ts`, web's `api.ts`), which the full check and GitHub cover (BOS-2334); it counts toward the hand run's 15-file skip. Every check-quick run, by hand or at the gate, also runs the test files in any package that name a string literal or one-line JSX text the branch removed from JS/TS source and did not add back (a label, aria name or Settings path; BOS-2386). These are at most 15 files (`CHECK_QUICK_REMOVED_MAX`), and a string found in more than 10 test files is left out as too common. The log lists each file with the string that picked it, under `INFO  tests that name a string the branch removed`. The same runs (and every queued check, which sets the same switch) also run the shell tests (`*.test.sh`) whose subject changed: the test itself, one that names a changed file by repo path or a changed file of its own folder by name, and the ones that read the repo's file list (`negated-redirect`, `shell-tests-needed`, about 4 s together), through `scripts/test-shell.sh`. A new test of either kind is picked up with nothing to add. A hand run skips them (`CHECK_QUICK_WHOLE_REPO=1` runs them).
- GitHub CI is the first full run for low and medium work, so a test that reaches code in another package by path (for example the server's owner-control list reading web pages) can still first fail there; the list guards in `scripts/check-guards.sh` cover the known ones.

**Squeeze report (BOS-2484, report only).** When every other step passed, check-quick ends by running `scripts/squeeze-test.sh` on up to 3 test files the branch added or changed (web, server, shared, launcher, updater; not the runner, and not the files in `scripts/squeeze-skip.txt`, which have their own GitHub limit). It prints a `SQUEEZE` line per file and a closing `check-quick: squeeze (report only): ...` line, and says how many files it left out. A `SQUEEZE  FAILED` line never fails the check or blocks a merge: it means the test failed on one slow, busy CPU, as GitHub's machines are, so look for a time limit or a short fixed sleep. "No answer" and "could not run" are not findings. `CHECK_QUICK_SQUEEZE=0` switches it off. It does not show races. The step is counted for two weeks (lines reported, fixed before merge, false alarms) and removed if its lines are ignored or more than 1 good file in 20 is reported.

Anything the gate reports blocks the merge.

- Changed `apps/server/src/db/schema.ts`? Generate the migration with drizzle-kit and commit it.
- Main took your migration number? Leave it. Do not renumber by hand: the merge gate renumbers a branch whose only clash is migration bookkeeping (`rebaseMigrations`, BOS-690), and `scripts/check-quick.sh` accepts that case, printing "migration NNNN will be renumbered to MMMM by the merge gate". A real clash (code, or the same table or column changed on both sides) still fails; see `docs/10-migrations.md`.
- Added a shell script or a `*.test.sh`? `git add` it: `scripts/check-shell.sh` ShellChecks every tracked `*.sh` and `scripts/test-shell.sh` runs every tracked `*.test.sh`. Only a file on a skip list in those scripts (each entry with its reason) is left out.

Changing a screen? If your branch changes `apps/web/src/styles.css`, `App.tsx` or the JSX of a page or component, the move to review needs a `*-render.test.tsx` in `apps/web/test` that loads `styles.css` in Playwright/Chromium and measures geometry (template: `merge-queue-held-render.test.tsx`; jsdom doesn't count). It also needs "before" and "after" screenshots from `scripts/screenshot.mjs --api` (only those carry the mark the check looks for), attached to the ticket. A change that doesn't alter the layout passes `noVisualChange: "<why>"` instead. See `docs/28-browser-checks.md` (BOS-2511).

The move to review also runs three list guards on your changed files (BOS-2522): a button or field label in a changed `apps/web/src` `.tsx` that `packages/shared/src/owner-controls.ts` doesn't hold, or a file with buttons missing from FILE_SCREEN; a new wake reason missing from WAKE_CLASS; a server file that newly reads an update hold and isn't in READERS. A miss refuses the move with the exact lines to add. It refuses only when the name is nowhere in the list, so the quick check still runs the full guards, and screen-inventory runs only there. If a refusal is wrong, move again with `listGuardWrong: "<why>"`.

A branch that changes owner-facing code (a non-test file under `apps/web/src`, or a server file in `OWNER_CARD_FILES` in `apps/server/src/services/surfaces-gate.ts`) also needs `surfaces: "<one line, up to 300 characters>"` on the move to review (BOS-2733): every screen, card or command form where you checked the change applies. It is kept in the state note as "Surfaces: …" and the reviewer judges whether the list is complete.

## Writing tests: they must pass on GitHub's runners too

A pass at the merge gate is not enough: GitHub CI runs every test again on main, on machines 2.5 to 5 times slower, with a newer git and a cold browser. Authors follow this rule and reviewers check every new or changed test against it:

- **No wall-clock limits tuned to a dev machine.** Time the work against a baseline run in turn on the same machine (`packages/shared/test/permission-judge.test.ts`, "stays fast on a 10,000-char line"), or give GitHub its own limit and say why (`apps/server/test/hot-path-budget.test.ts`, `LIMIT_MS`). Either way, say in a comment what the limit still catches.
- **No fixed sleeps standing in for "the other side is ready".** Wait for the event: the port answering, the line in the log, the file appearing, with a deadline.
- **No hidden stderr** (`2>/dev/null`) on a step whose failure would end the test silently.
- **A test that needs a build or a browser runs at the gate, not quietly skips there.** Make sure the gate (and CI) supply what it needs before relying on it. In the full check a test file that skips fails the step unless it is listed, with a reason, in its package's `skipped-tests.txt` (`scripts/skipped-tests.txt` for the script tests; `scripts/check-no-skips.mjs`, BOS-1729).
- **A flake fix shows the test failing before and passing after.** Run `scripts/squeeze-test.sh <test file>` (one file, one worker, one CPU shared with busy loops, 200 s stop) on the old test and on the fixed one, and put both results on the ticket. It shows a time-limit flake only: a race between processes or a too-short fixed sleep may pass under it, so say so if it did.
- **The ratchet.** `scripts/check-test-lines.mjs` (in check-quick, check-all and CI) counts five shapes per file, on code (comments and strings are blanked, wrapped statements matched whole): a bare sleep outside a polling loop (any delay, literal or variable; a `for...of` is not a poll), an elapsed limit (`expect(elapsed)`, `expect(t1 - t0)`, `expect(ms)` with `.toBeLessThan`), a sum on a fresh clock read (`Date.now()`, `new Date().getTime()`) inside an `expect`, a read file cut to a fixed length (`readFileSync(x).slice(0, n)`, or a later `text.slice(0, n)` on what it returned), and hidden stderr (`2>/dev/null`, `2> /dev/null`, `&>/dev/null`, `>/dev/null 2>&1`, `2>&-`) on a test step — the last one matched on the raw line, since the redirect usually sits inside a string passed to `execSync`/`spawn`, so `*.test.sh` files are scanned too (BOS-2794). A word in a comment (`baseline`, `for (`) does not exempt a line. The counts in `scripts/test-lines-baseline.json` may only go down: a new hit fails and prints file and line. Allowed: a sleep inside a `while`/`for` poll or a helper named waitFor, waitUntil, poll*, eventually, until*, retry*; a limit on a line naming `LIMIT_MS` or `baseline`; `// test-lines-ok: <why>` (or `# test-lines-ok: <why>` in a shell test) on or above a line. When you remove a hit, run `node scripts/check-test-lines.mjs --update`; never raise the baseline.
- **Web tests: stub fetch by URL with the shared helper.** `stubFetchByUrl({ "/api/…": body })` (jsdom) or `urlStub` (a browser test's server), in `apps/web/test/stub-fetch.ts`, answers each path with its own shape and fails the test with "no stub for GET /api/…" on any request it has no answer for. Never one reply for every URL, or an "anything else" fallback: the page then reads a wrong shape and errors only on GitHub (BOS-2425, BOS-2420).
- **Don't depend on git's version.** Tests that read git output must not rely on its ordering or on refs a newer git adds; sort, or ask for exactly the refs you need.

## Running a full check by hand

Inside an agent session `check-all.sh` refuses to run: use `scripts/check-quick.sh` (above). When the CEO asks for a full run, set `CHECK_ALL_FORCE=1` and start it detached, never as a harness background task (the harness kills those when your run ends):

```
CHECK_ALL_FORCE=1 setsid nohup scripts/check-all.sh > "$(git rev-parse --git-dir)/check.log" 2>&1 &
```

Read that log for the `check-all: everything passed` line or a non-zero exit. A check that was signalled writes `check-all: killed by signal <name>` to the log and frees its queue place. Never kill another agent's process (no `pkill -f check-all.sh`, no `killall`): that kills their queued checks.
